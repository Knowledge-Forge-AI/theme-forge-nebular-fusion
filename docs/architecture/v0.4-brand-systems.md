## Purpose and controlling theorem

Studio is now an independently locked application under `apps/studio` in this
same repository. Core, protocol, sidecar, fixtures, and application may share
one atomic source candidate, while package, version, artifact, capability,
agent-context, and post-release rollback identities remain separate. The root
npm package is not a workspace and does not include Studio.

The controlling implementation sequence is TFSB47H (in-repository bootstrap),
TFSB47I (sidecar host/transport), TFSB47J (live reads), TFSB47K (typed plans),
TFSB47L (human-agent evidence freeze), TFSB48 (Terminal Nova dogfood), TFSB49
(PR/CI and macOS-arm64 qualification), TFSB50 (coordinated release candidate),
and TFSB51 (attended publication and post-release smoke).

The expanded v0.4 program adds brand family semantics, token/recipe authority,
QA and diff, reusable distribution, optional PNG export, and typed Studio
surfaces to the already implemented collection/workspace/service
infrastructure. Public v0.3.0 remains immutable. Package/source version stays
0.3.0 until the later release-candidate phase.

The controlling theorem is:

```text
brand metadata may coordinate existing bounded authorities
  != generic file, XML, script, network, legal, or cross-project authority
```

Brand features are opt-in. Absence of `.tfsb/brand.toml` preserves exact
schema-1/schema-2 and package-0.3.0 behavior.

## Closed terminology

| Term | Exact v0.4 meaning | Not equivalent to |
| --- | --- | --- |
| brand system | The validated family/binding file plus its declared token, recipe, QA, consumer-profile, package, and export domains and referenced asset digests | SVG schema, project, workspace |
| brand package | One owner-versioned distributable brand identity and inventory described by `brand-package.toml` and compiled `tfsb-brand-manifest.json` | npm package, generic bundle manifest |
| family | A named set of related assets jointly representing one identity | directory, collection, shard |
| role | An explicit intended communicative use such as `mark` or `favicon` | filename heuristic, install destination |
| variant | A family-local treatment identity with background, color, scale, status, and size metadata | a copied file or implicit theme |
| asset binding | One explicit mapping from an existing canonical asset ID to one family/role/variant triple | SVG metadata, source-map entry |
| required role | A declared completeness predicate that must resolve to exactly one binding | an inferred conventional filename |
| optional role | A declared permitted omission or exact optional binding | wildcard or fallback |
| palette/token | A typed named color, linear gradient, dimension, or opacity value owned by `brand-tokens.toml` | CSS custom property, expression language |
| derivative recipe | A closed ordered transformation over a parsed source asset and typed tokens | script, selector language, arbitrary XML rewrite |
| derived asset | A materialized schema-2 canonical asset owned by one recipe and one receipt | human-edited source asset, build output copy |
| source asset | An owner-edited canonical asset that is not a recipe target | filesystem source path or source-map record |
| QA profile | A named, versioned selection of bounded semantic and visual QA cases | Playwright configuration or arbitrary test script |
| QA case | One closed assertion against an exact asset/binding and optional render configuration | generic test command |
| visual baseline | Owner-approved PNG golden bound to case, input, renderer, dimensions, and digest | source SVG or geometry proof |
| consumer profile | A versioned list of typed asset/companion selectors and fixed confined destinations | generic copy/template engine, project install declaration |
| consumer lockfile | Canonical consumer record of exact package/profile/input/output identities | source fetch configuration, package-lock replacement |
| package manifest | Owner-authored brand package semantics and its compiled brand companion manifest | `tfsb-manifest.json` byte inventory |
| legal companion | Byte-preserved owner-authored guidance/license/notice/trademark-purpose file | inferred permission or synthesized license conclusion |
| export profile | Closed PNG output selection, dimensions, background, color, alpha, and destination policy | arbitrary renderer options or postprocessor |
| raster receipt | Canonical proof of exact source/profile/adapter/configuration/output identities | claim of universal visual equivalence |
| brand semantic diff | Typed structural changes across inventories, tokens, recipes, package, profiles, QA, and exports | pixel comparison |
| brand visual diff | Renderer-bound pixel measurements for exact cases | geometry equivalence proof |
| Studio brand surface | Additive typed `tfsb.studio` protocol 1.1 brand capabilities over existing handles/plans | filesystem, shell, CLI, or Tauri RPC bridge |

Source map, shard manifest, workspace, bundle manifest, SVG schema, and project
install declarations retain their existing meanings. Brand records may refer to
their identities but never absorb their authority.

## Canonical domain topology

```text
.tfsb/project.toml                     existing project/install authority
.tfsb/assets/*.toml                    existing schema-1/schema-2 assets
.tfsb/brand.toml                       brand presence, families, bindings
.tfsb/brand-tokens.toml                typed token authority
.tfsb/brand-recipes.toml               closed derivation authority
.tfsb/brand-qa.toml                    semantic/visual QA authority
.tfsb/consumer-profiles.toml           reusable producer install profiles
.tfsb/brand-package.toml               owner package/legal metadata
.tfsb/brand-exports.toml               optional PNG export profiles
.tfsb/derived/*.receipt.json           generated-asset receipts
.tfsb/brand-baselines/**/*.png         owner-approved visual goldens

consumer/.tfsb/brand.lock.json         installed package/profile/output lock
bundle/tfsb-manifest.json              existing generic byte inventory
bundle/tfsb-brand-manifest.json        compiled brand semantic companion
```

The seven owner-authored files have independent schema identifiers and version
1. `brand.toml` is the presence marker and declares which fixed companions are
enabled. Unknown keys/versions and undeclared companion files fail. There is no
path indirection. Each file is at most 1 MiB.

Canonical semantic DTOs use recursively UTF-8-byte-sorted object keys, schema-
declared array ordering, safe integers, exact strings, and no whitespace. Each
file digest is `sha256("<schema-id>-v1\n" || canonical-json)`. The brand-system
digest combines `brand`, `tokens`, `recipes`, `qa`, `consumerProfiles`,
`exports`, and referenced canonical asset digests under `tfsb-brand-system-v1`;
the package then binds that digest without a cycle. Full rules are in ADR 0012.

No project or SVG schema 3 is introduced. Existing projects with no brand files
do not load this topology and retain byte-for-byte lifecycle behavior.

## Families, roles, variants, and completeness

Family and variant IDs use 1..64-byte ASCII kebab IDs. Built-in roles are:

```text
mark
wordmark
lockup-horizontal
lockup-stacked
favicon
app-icon
avatar
social-card
```

Operator roles require `x.<namespace>.<name>` with validated kebab namespace
and name. They add identity, not behavior. Files never imply roles.

Each variant freezes:

- backgrounds: one or more of `light`, `dark`, `transparent`, or only `any`;
- color mode: `full-color`, `monochrome`, or `reversed`;
- scale: `standard` or `simplified`;
- status: `primary` or `secondary`;
- optional minimum width/height in exact pixels; and
- a display-order integer used only for human presentation.

One family/role/variant triple resolves to exactly one asset. One asset may bind
to multiple triples only through explicit records, with at most eight bindings
per asset. Overlapping primary matches fail; secondary assets require exact
selection. Required-role predicates can constrain background/color/scale and
must each resolve once. Optional roles are declared omissions, not fallbacks.
Digests and machine lists ignore display order and use canonical ID order.

Terminal Nova's proposed `terminal-nova` family demonstrates:

- full-color primary marks for light and dark backgrounds;
- full-color horizontal and stacked lockups for light and dark backgrounds;
- simplified primary favicons for light and dark backgrounds;
- two monochrome secondary marks, one of which is the reversed/on-dark
  treatment; and
- explicit zero-destination bindings for those monochrome marks.

The ten exact observed asset identities and proposed records are under
[the example tree](../examples/v0.4/brand-system/README.md) and
[the projection](../evaluations/v0.4-terminal-nova-brand-projection.md).

## Token and derivative authority

Tokens are closed typed values: canonical RGBA color, linear gradient,
integer/unit dimension, or millionth opacity. There is no generic expression,
arithmetic, environment fallback, CSS cascade, or asset-TOML token reference.
References are typed, missing/type-mismatched references fail, the graph is
acyclic with depth at most eight, and unused tokens are warnings.

Recipes consume exact canonical source asset IDs and produce different exact
target IDs. The closed operations are exact paint replacement, monochrome,
remove one named group, retain exact named top-level groups, add one bounded
background plate, resize only canvas/viewBox, copy accessibility by closed
policy, and copy explicitly listed metadata. Every paint/group operation has
expected counts.

Recipes operate on parsed typed models. JavaScript, shell, XPath, CSS selectors,
regex, globs, numeric structural paths, arbitrary XML/TOML mutation, plugins,
network, and filesystem reads are forbidden. The recipe graph is acyclic,
maximum depth 8, maximum 128 recipes/derived targets, and 16 operations per
recipe.

Targets are explicit schema-2 assets with generated receipts. Recipe plus
tokens is sole authority. A target missing its receipt, a receipt missing its
target, or any human byte drift blocks build/derive with no overwrite.
Derivation occurs only through an explicit plan/apply and existing project
transaction. Sources plus targets retain the existing 128-asset, 8-MiB each,
and 32-MiB selected mutation limits.

## Brand package and legal companions

`brand-package.toml` owns package ID/name/brand SemVer, family/role inventory,
required companions, owner-authored legal/trademark-purpose metadata, domain
digests, compatible consumer profiles, and bundle asset digests. TFSB never
infers permission from files, SPDX strings, repository visibility, or software
licenses.

Companions are exact regular files with producer source path, fixed bundle path
(`companions/<canonical-file>`), explicit `canonical_companion_file` under `.tfsb/companions/`,
media type (`text/markdown` or `text/plain`), purpose, required flag, and byte digest. They are copied
byte for byte, never normalized or mutated, and cross-checked against both manifests. Canonical companion
filenames must satisfy `isAllowedCompanionFilename`. Terminal Nova's
`brand/README.md -> companions/README-BRAND.md -> .tfsb/companions/README-BRAND.md -> README-BRAND.md`
relationship is modeled via Option A from ADR 0017, storing the canonical file
under `.tfsb/companions/README-BRAND.md` upon import while preserving producer
metadata as historical authority without writing outside `.tfsb`. When rebundling from an imported project,
provenance check (`import.kind == "archive"`) verifies the canonical companion against declared digest when
producer source is absent.

All seven fixed owner-authored brand files (`brand.toml`, `brand-tokens.toml`, `brand-recipes.toml`,
`brand-qa.toml`, `consumer-profiles.toml`, `brand-package.toml`, `brand-exports.toml`) follow a normative
1:1 round-trip bundle mapping: `.tfsb/<fixed-name>.toml` <-> `brand/<fixed-name>.toml` <-> `.tfsb/<fixed-name>.toml`.

`tfsb-brand-manifest.json` accompanies `tfsb-manifest.json` (which uses schemaVersion 2
for brand bundles) and binds generic manifest raw byte digest (`genericManifestByteDigest`),
brand-package digest (`brandPackageDigest`), brand-system digest (`brandSystemDigest`),
domain digests, sorted inventory with distinct `canonicalAssetDigest` (TOML-basis semantic digest via
`computeAssetSemanticDigest(asset)`) and `svgDigest` fields, profiles, and companions, sealed with self-digest
`brandManifestDigest`. Total bundle archive entries are strictly bounded to at most 514 entries (512 payload
plus the two reserved manifests). Offline import verifies generic bytes first, then brand semantics, before
executing a single atomic transaction. No registry/license/trademark/network lookup occurs.

## Consumer profiles and lock

A profile contains closed enum parameters and exact output rules. Rules select
one exact asset, family/role/variant predicate, or companion and map it to a
fixed relative destination or fixed directory with a closed filename policy.
Parameters influence only equality conditions and binding choice; paths never
contain placeholders. Every collision policy is `error` in v1.

At most four qualified profiles compose directly by canonical ID order;
composition is acyclic, at most four levels deep, and selects at most eight
profiles per lock. There is no
override, last-writer-wins, deletion, script, glob, regex, environment value,
URL, or generic source copy. Destination validation uses existing project-root,
no-follow, case/portable-collision, protected-source, unowned-output, and
transaction rules. Producer profiles contribute to `brandSystemDigest`;
consumer-local profiles remain separate authority in an unbranded project.
One consumer root is one transaction.

Required producer examples are:

- `astro-starlight`: six brand assets under `docs/src/assets/brand/`, exact
  light/dark favicon paths under `docs/public/`, alias `docs/public/favicon.svg`,
  and required `README-BRAND.md`;
- `vite-web`: selected brand assets under `src/assets/brand/` and the selected
  favicon at `public/favicon.svg`; and
- `package-distribution`: all ten assets under `brand/dist/` plus required
  legal/brand companions.

Existing explicit project installs stay valid. Ownership transfer to a profile
requires an explicit equal-byte migration.

`.tfsb/brand.lock.json` binds exact package/bundle/system/token/recipe/profile/
export digests, selected enum values, role mappings, destination bytes, and
companion identity. It contains no absolute paths, network source, host/user,
timestamp, credential, or companion content. Only successful
install/sync/adopt apply updates it with outputs through one authenticated
transaction: per-parent sibling staging, deterministic output promotion, lock
last, handled rollback, and truthful recovery residue. This does not claim
cross-directory power-loss atomicity. Check works offline and distinguishes
`ok`, `source-unavailable`, `stale`, `drift`, `collision`, and `invalid`.

## Declarative QA

QA separates semantic core from explicit renderer capability.

Semantic cases cover inventory/completeness, accessibility consistency,
palette/token conformance, external references, embedded raster/fonts, recipe
state, and canvas/minimum-size declarations. Visual cases cover exact pixel
sizes/backgrounds, visible/transparent bounds, padding, clipping, small-size
visibility, and owner-approved PNG baselines.

Machine JSON is the result authority; Markdown and scriptless HTML are escaped
projections. Stable exit codes are 0 pass, 1 invalid/runtime error, 2 assertion
failure, and 3 required capability unavailable. Normal QA and CI cannot update
goldens. Baseline update is a typed plan/apply with old/new image and semantic
diff. Playwright remains a repository development dependency, not hidden
product QA runtime.

## Brand-aware diff

Brand semantic diff has closed sections for inventory/completeness, bindings,
tokens/palette, recipes/receipts, canvas/typed geometry/bounds, QA impact,
package/legal, consumer destinations/lock, and exports. It is available as
canonical JSON, Markdown, and Studio DTO while preserving generic diff.

Visual diff is renderer-bound and reports exact case/input/renderer identity,
pixel changes, channel delta, changed bounds, and image digests. Pixel equality
is evidence for that case only; it never proves geometry equivalence.

## Raster and platform-icon boundary

Core parses bounded export profiles and produces pure plan DTOs but has no
raster runtime dependency, plugin loader, or install-time download. A separate
fixed optional companion, `@knowledge-forge-ai/tfsb-raster-resvg`, binds
`@resvg/resvg-wasm@2.6.2` and the reviewed local WASM artifact. The base loader
uses no user-selected module path and reports capability unavailable when that
exact companion/tuple is absent or incompatible. The companion exposes only the
closed `resvg-png-v1` adapter after dependency, license, supply-chain, package,
and deterministic-qualification review.

Required v0.4 outputs are PNG. Apple-touch, PWA, avatar, and social-card are
closed PNG purposes. ICO and ICNS are unsupported until a separately qualified
adapter proves exact format/platform behavior. SVG remains canonical.

Profiles freeze selection, destination, dimensions, fit/pad, background, sRGB,
and alpha. They forbid external resources, fonts, embedded raster, arbitrary
crop/filter/postprocessing, network, and ambient metadata. Receipts bind pinned
adapter/renderer/build/platform, source asset/SVG/brand-system digests, export-file/
profile/output-configuration digests, PNG digest, decoded-pixel digest, and
qualification ID (with canonical bases frozen in ADR 0015). Determinism is claimed
only for tuples that pass repeated clean-process byte equality; otherwise capability
is unavailable and no partial required output is published.

## Studio surface and coordinated readiness

Brand methods are introduced as `tfsb.studio` protocol 1.1 capabilities with
strict backward-compatible negotiation for protocol 1.0 clients. Reads cover
status, family/role/variant inventory, tokens, recipe graph, QA profile/results,
brand diff, consumer profiles/lock, and export capability/status. Pagination,
16-MiB frames, sanitized DTOs, existing handles, and cursor staleness remain.

Typed derive, baseline, consumer install/sync, and export plans exist only
after the corresponding core domain planner/executor. They use the existing
private plan registry and `plan.apply`; public DTOs are not authority. No new
absolute-path method, generic TOML editor, filesystem, shell, CLI, module, or
network RPC is added.

The independently locked Tauri 2 + React Studio under `apps/studio` owns UI,
native selection, sidecar supervision, target-triple packaging,
signing/notarization, and desktop capabilities. Rust does not parse `.tfsb`;
React receives no filesystem/shell authority. Shared source does not permit
frontend imports of private core modules.

Release readiness is coordinated but artifact publication is separate. TFSB50
cannot accept the expanded release until the exact public source candidate has
authenticated core and Studio package evidence. Both initial tags target that
source commit, while products retain independent versions, artifacts,
publication records, compatibility, and rollback.

## Compatibility and migration

No implicit migration exists:

1. existing schema-1/schema-2 projects continue unchanged without brand files;
2. add family/variant/binding metadata without changing assets;
3. lift literal colors into tokens only through an explicit reviewed mapping;
4. add recipes only after source/target authority and initial output diff are
   accepted;
5. transfer explicit install ownership only after exact equal-byte proof; and
6. create a consumer lock only through a successful local bundle/npm-installed
   plan/apply.

Archive, directory, shard, workspace, preview, bundle, generic diff, current
public API, and protocol 1.0 non-brand behavior remain compatible. Brand files
are included in bundles only when present and declared.

| distinct roles | 64 |
| variants | 256 |
| bindings | 1,024; 8 per asset |
| tokens / token references | 256 / 1,024 |
| recipes / graph depth / operations per recipe | 128 / 8 / 16 |
| QA profiles / all cases / visual cases | 32 / 512 / 256 |

Workspace brand reads retain 1,024 bounded children but load one project and
one page at a time. There is no workspace mutation, no cross-project or
cross-repository transaction, no network source fetching, no arbitrary plugin,
no unowned output deletion, and no source/legal companion mutation.

## Development branch and CI policy

TFSB47A is the architecture transition on `main`. After it lands via dispatcher
publication, the operator creates or selects `v0.4-brand-systems`. Implementation
phases TFSB47B through the final implementation-hardening phase use
`v0.4-brand-systems`. Ordinary pushes to that branch intentionally run no
Actions. The operator does not open its PR against `main` until TFSB49
intentionally starts complete qualification. Opening, later synchronizing, or
reopening that PR runs CI; superseded in-progress runs for the same PR cancel.
Final release acceptance reviews the exact PR head that passed CI. Direct
implementation pushes to `main` are not the normal expanded-v0.4 flow.

The full exact branch and phase contract is
[the expanded roadmap](../implementation/v0.4-brand-systems-roadmap.md).

## Completion and non-goals

TFSB47A freezes architecture, examples, assignments, supersession, and the
PR-only workflow. It implements no product brand runtime. Later phases must
provide executable parser, lifecycle, safety, determinism, package, Studio, and
Terminal Nova evidence before v0.4 acceptance.

Non-goals are arbitrary SVG/XML/CSS mutation, expression languages, scripts,
plugins, network fetching/rendering, legal inference, generic copy templates,
cross-repository atomic writes, mandatory raster dependencies, unproven
ICO/ICNS support, merging Studio into the root npm package or core runtime, and
any mutation or publication of Terminal Nova during this phase.
